# AdMob Ads Implementation Plan

> **For Codex workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` or `executing-plans` task by task. Every checkbox is a separate action.

**Goal:** Ship genuine Android AdMob rewarded revive and sparing interstitial ads, while preserving deterministic placeholder ads for desktop, headless, and `PIPE_TEST`.

**Architecture:** Keep the existing `Services.ad` interface and deferred signal contract. A thin real adapter is selected only for Android exports explicitly marked `admob_test` or `admob_live`; test uses Google demo IDs. All other environments use the deterministic stub. A small pure resolver selects the adapter from an environment snapshot so the guard matrix is unit-testable.

**Out of scope:** Play Billing / Remove Ads, online leaderboards, mediation, analytics, banners, and any external backend. Live builds must hide the existing Remove Ads action until a separate billing plan exists.

## File map

- Modify: `scripts/monetization_config.gd` — explicit test/live ID selection and safe runtime guards.
- Modify: `scripts/services.gd` — retain stub; select the plugin adapter only for a guarded Android live/test build.
- Create: `scripts/ad_service_admob.gd` — plugin-specific rewarded/interstitial adapter after its actual API is verified.
- Modify: `scripts/main.gd`, `scripts/screen_controller.gd`, `scripts/view/runover_view.gd`, `scripts/view/settings_view.gd` — failure-safe revive and live-mode UI gating.
- Modify: `export_presets.cfg`, `tools/android-preflight.ps1`; create `tools/export-ads-build.ps1` — explicit test/release exports.
- Modify/create focused tests beside the existing GUT service/screen tests and PowerShell structural tests under `tests/`.
- Modify: `docs/MONETIZATION_SETUP.md`, `docs/HANDOFF.md`, `docs/store-listing.md`.

## Phase 0 — human-only setup, complete this first

Browser automation can open the pages and copy the non-secret IDs; you must sign in, accept terms, submit forms, pay, and approve any external changes.

1. Open [AdMob](https://admob.google.com/). Sign in with the publisher Google account; complete account, identity, and payment verification. AdMob review may take time.
2. In [Apps](https://apps.admob.com/v2/apps), create the Android app using the final package ID `org.aqueduct.game`. Record its **App ID** (`ca-app-pub-…~…`).
3. Under that app's [Ad units](https://apps.admob.com/v2/apps), create exactly two units: `revive_rewarded` (Rewarded) and `between_runs_interstitial` (Interstitial). Copy both IDs (`ca-app-pub-…/…`). Do not create a banner or mediation group.
4. In [AdMob test devices](https://apps.admob.com/v2/settings/test-devices), add the physical Android device that will test production IDs. Do not click an ad until it is labeled **Test Ad**.
5. Publish a public privacy-policy URL and an `app-ads.txt` file at the developer website root; paste the privacy-policy URL into Play Console later. If operating in EEA/UK/Switzerland, choose and configure the consent-message flow in AdMob before live release.
6. Create a Google Play developer account and internal-testing release access at [Play Console](https://play.google.com/console/). This is required only for the final AAB delivery test; it does not authorize billing implementation.
7. Provide the implementation worker the three copied AdMob IDs, privacy-policy URL, and the exact installed plugin archive/version. Keep the signing keystore and passwords local; never commit them.
8. Generate a release upload keystore and provide only its local path and alias to the worker; provide passwords through local environment variables when prompted. Never paste them into a plan, chat, source file, or repository.

**Browser lane and handoff artifact:** a browser-assisted worker opens the four linked consoles, verifies the visible current page/title, and copies only the App ID, two unit IDs, and test-device confirmation into a local handoff note. It must stop for login, terms, consent, payment, resource creation, test-device registration, or Play upload confirmation. The human returns the three IDs, plugin archive/version, privacy-policy URL, and `TEST_DEVICE_REGISTERED=yes`.

## Phase 1 — pin and inspect the plugin

- [ ] Install one Godot 4.6-compatible AdMob plugin into `addons/` using its official release instructions; install its required Android dependency/template changes.
- [ ] Record its exact release/tag and inspect the actual `plugin.cfg`, Android export settings, singleton/classes, load/show methods, reward/interstitial terminal signals, and callback semantics. The chosen plugin must support UMP consent before Mobile Ads initialization; otherwise stop and choose a compatible plugin before writing adapter code. Do not code against documentation from a different plugin version.
- [ ] Run `& '.\tools\android-preflight.ps1'`; it should remain green before changing export configuration.
- [ ] Create a failing structural test that asserts the selected plugin exists, its version is pinned, and `PIPE_TEST` never selects `AdServiceAdmob`, initializes Mobile Ads/UMP, or invokes a plugin method.

## Phase 2 — establish test/live configuration before adapter code

- [ ] Write failing GUT tests for `MonetizationConfig`: `admob_test` selects all three Google demo IDs; `admob_live` selects nonempty non-demo IDs; desktop/headless/`PIPE_TEST` selects the stub.
- [ ] Add an enum-like mode with only `STUB`, `TEST`, and `LIVE`; add Google Android demo IDs: App ID `ca-app-pub-3940256099942544~3347511713`, rewarded `ca-app-pub-3940256099942544/5224354917`, and interstitial `ca-app-pub-3940256099942544/1033173712`.
- [ ] Keep production IDs blank until Phase 0. `LIVE` must reject blank/demo values. The verified plugin must inject the selected App ID into its generated manifest; never hand-edit a generated manifest.
- [ ] Use `OS.has_feature("admob_test")` and `OS.has_feature("admob_live")` as the exact mode lookup. Set `custom_features="admob_test"` for `Android Test` and `custom_features="admob_live"` for both `Android Live Device` and `Android Live`; assert no other preset has either literal.
- [ ] Select an AdMob bootstrap adapter only when Android OS, not `PIPE_TEST`, exactly one explicit feature, plugin enabled for that export preset, and valid App/unit IDs hold. Consent is not a resolver input. Every other condition keeps `AdServiceStub`.
- [ ] Add a pure `resolve_ad_mode(environment: Dictionary)` seam accepting Android, custom features, `PIPE_TEST`, plugin availability, and ID validity. Test every selection/denial combination; have `Services._ready()` build the real environment snapshot and call only this resolver. The selected real adapter resolves consent internally and remains no-op until `READY`; all request attempts before READY/after denial emit their matching deferred failure signal.
- [ ] Run the focused GUT test: expected red before config, then green; run `& '.\tools\run-gate.ps1'` and require exit `0`, positive tests/assertions, exactly one quarantined control.

## Phase 3 — integrate the smallest real adapter

- [ ] Add a fake adapter callback harness, used only by GUT, that exposes reward earned/closed/failed, interstitial closed/failed, and consent-resolved callbacks. Test that `show_rewarded("revive")` emits success only after fake reward-earned; test failure/close emits one failure; test interstitial terminal signals do not alter game state directly. Actual `admob_test` Android builds do contact AdMob with demo IDs; only headless/GUT stub and fake-adapter paths make no network call.
- [ ] Freeze the shared contract: `reward_earned(kind)`, `reward_failed(kind)`, and `interstitial_finished()` signals; each request has exactly one terminal signal. Make stub, fake, and real adapters implement them. The stub defers `reward_earned` for rewarded and defers `interstitial_finished` for interstitial.
- [ ] Create `ad_service_admob.gd` using only the verified Phase-1 API. Its states are `CONSENT_PENDING`, `CONSENT_DENIED`, `READY`, and `SHOWING`; UMP consent must reach `READY` before SDK initialization/preload. Consent denial/failure stays `CONSENT_DENIED` (no ads). It preloads one rewarded/interstitial, emits reward only from the SDK reward callback, and emits one `interstitial_finished()` after close/failure before reload.
- [ ] Update `Services` to load the adapter dynamically only after the Phase-2 guard. Keep `Services.iap` stubbed in every ads preset and add a structural test proving Billing cannot be selected.
- [ ] Focused tests green, then full gate green.

## Phase 4 — make the shipped UI failure-safe

- [ ] Add failing tests for: Revive leaves Run Over visible while an ad is loading/showing; a second tap is ignored while pending; only the first `reward_earned("revive")` dismisses it and revives once; failure then a late reward is ignored; cancellation/load failure preserves score and shows `Ad unavailable. Try again.`
- [ ] Change `main.gd`/screen controller so the overlay is dismissed immediately before the successful revive, not when the ad request starts. Track one pending `"revive"` request and accept exactly one terminal callback.
- [ ] Add a small status label to `runover_view.gd`; clear it and disable Revive while pending, then re-enable it on failure.
- [ ] Change the between-run route to keep the current menu/run-over surface visible, disable its New Game control, and request the interstitial. Start the next game exactly once from its closed/failed terminal signal, then re-enable the control only if the user remains on that surface. Add tests proving no duplicate tap and no gameplay behind an interstitial.
- [ ] Use this cadence table: session start → no ad; completed run 1 → no ad; completed run 2 → one ad; completed run 3 → no ad; completed run 4 → one ad. A run ends only through normal clear/fail resolution; revive remains the same run; abandoning to Menu does not increment the counter. Add focused tests for every table row.
- [ ] Hide Remove Ads for `TEST`/`LIVE` until Billing is implemented. In those modes ignore the legacy locally persisted `ads_removed` flag for ad suppression, because it may have been written by the old fake purchase; preserve the raw value only for a later entitlement-migration plan.
- [ ] Run focused tests, then the full gate. Exercise the normal non-`PIPE_TEST` desktop path only as a UI smoke test—it proves no layout regression, not ads.

## Phase 5 — explicit export automation

- [ ] Write failing PowerShell tests asserting three intentional presets: `Android Test` (debug APK + only `admob_test`), `Android Live Device` (signed release APK + only `admob_live`), and `Android Live` (signed release AAB + only `admob_live`). Assert the existing `Android` preset stays prebuilt-template, Gradle-free, and feature-free.
- [ ] Update `export_presets.cfg` only after the plugin/template is installed. Record the chosen plugin's exact per-preset export setting/key that supplies the Test sample App ID and the Live production App ID. Enable Gradle/plugin only for the three ads presets and retain the existing `Android` preset unchanged. Assert exported manifests: Test has the sample App ID; Live has the production App ID; legacy Android has neither AdMob dependency nor App ID.
- [ ] Replace `-AdMode` with `-Target Android|Test|LiveDevice|LiveBundle` in `tools/android-preflight.ps1`. Parse only that target preset; require NDK/plugin/Gradle only for ads targets, require production IDs/signing only for LiveDevice/LiveBundle, and validate the human-provided release-keystore path/alias without printing secrets.
- [ ] Add `tools/export-ads-build.ps1 -Target Test|LiveDevice|LiveBundle` that passes the same target to preflight then exports exactly one artifact to `C:\Temp\aqueduct-test.apk`, `C:\Temp\aqueduct-live.apk`, or `C:\Temp\aqueduct-live.aab`; never fall back from Live to Test.
- [ ] Run Pester structural tests, `run-gate.ps1`, and Test preflight; each must exit `0`.

## Phase 6 — device and release proof

- [ ] Export/install Test: `& '.\tools\export-ads-build.ps1' -Target Test`; `adb start-server`; `adb install -r 'C:\Temp\aqueduct-test.apk'`.
- [ ] In the normal UI, reach Run Over, complete a rewarded revive, and prove exactly one revive with preserved score. Close a second rewarded ad early and prove no revive plus error text.
- [ ] Prove first-session interstitial suppression, one eligible between-run test interstitial, no duplicate input, and later reload.
- [ ] Export/install LiveDevice only after test-device registration. Production IDs must still render a **Test Ad** label; if not, do not click.
- [ ] Before installing an artifact signed by a different certificate or switching from local release APK to Play delivery, run `adb uninstall org.aqueduct.game`; confirm success, then install the next artifact. Do not use `-r` across signing contexts.
- [ ] Export LiveBundle, upload it to Play internal testing, install through Play, and repeat the smoke tests. Complete Data safety/privacy-policy declarations manually.

## Rollback and acceptance

- [ ] Acceptance: full gate exit `0`; test APK shows labeled test ads; production-ID APK shows labeled ads only on the registered test device; release AAB installs through Play; no billing/leaderboard code added.
- [ ] Rollback: pause the Play rollout, blank live IDs/remove `admob_live` from the release preset, export a replacement, and rerun gate/preflight. Do not delete AdMob resources.
